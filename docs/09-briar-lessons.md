# 09 — 借鉴 Briar 的设计

> Briar（briarproject.org，Android 应用，**GPLv3-only**）是与本项目最接近的参照：同样是端到端加密、同等 UI 完成度、同为 GPLv3。本文只记录**可借鉴**与**必须拒绝**的部分，不改变 docs/02 的协议路线。
>
> 调研时间 2026-10；Briar 于 2026-07-09 进入 maintenance mode，官方归因包括高耗电、后台不可靠、加好友难用、缺备份与附件。

## 1. 可借鉴

### 1.1 指纹与信任建立的交互（M2 直接采用）

Briar 区分 `verified`（面对面验证）与 `unverified`（远端/他人介绍，可被 MITM）。其远程加好友最大的坑是：用户只发了链接没收到对方链接，界面永远停在 "connecting"。对此的解法值得照抄：

| 做法 | 落到本项目 |
|---|---|
| 双栏确认：我方已发出 + 对方已收到，各自打勾才能继续 | 加密信息页显示「我已把指纹发回对方 / 对方已核对」双状态 |
| 独立的「待处理请求」页面 + 超时后明确提示删除重试 | 信任请求列表，超时提示重新验证 |
| 面对面验证：双方同屏显示各自二维码，约 30 秒自动成环 | 指纹页「显示我的码 / 扫描对方」同屏，附进度与超时 |
| 指纹文案强调「确认你在跟正确的人说话」，而非「验证指纹」 | 同类文案，用于降低用户跳过验证的概率 |
| 经他人介绍拿到的公钥一律标 `unverified`，不得自动信任 | 若后续支持「群内加好友」，必须二次面对面验证 |

指纹展示沿用本项目不变量 4：A/B 两轨共用身份密钥指纹，因此**一次比对覆盖两条轨道**，这是本项目相对 Briar 的简化优势，应当在 UI 上明确说明。

### 1.2 传输层抽象（M1 预留）

Briar 用 `DuplexPlugin` / `SimplexPlugin` 把上层协议与具体传输解耦。本项目对应做法：

- `XmppService` 内部已是传输无关的 `Manager` 组合，后续 MAM、推送、账号迁移都以 manager 形式插入，不侵入业务层。
- 离线投递语义与 Briar 的 Mailbox 等价物是 **MAM + 服务端离线存储**，不必自造。

### 1.3 省电设置项（M6/M7）

Briar 的省电开关很朴素：`连接方式` / `允许移动数据` / `仅充电时连接`。本项目对应做成两档 `实时 / 省电`（实时=前台常驻长连接，省电=依赖推送唤醒），外加「仅充电时保持实时」。同时设置页应内置 OEM 后台管理引导入口。

## 2. 必须拒绝

| Briar 的做法 | 本项目为何不采纳 |
|---|---|
| 自研传输与加密栈（Bramble/BTP/BSP） | 与 XMPP 联邦不互通，「Briar 只能和 Briar 说话」。本项目坚持 XEP-0384 OMEMO + XEP-0060/0313/0198/0380 |
| Tor 常驻 + 前台服务常开 | 与联邦服务器模型冲突，耗电且难以推送唤醒。Briar 的维护公告已把「后台不可靠」列为躺平原因之一 |
| 自造邮箱服务扩展消息可达性 | 服务端已有 MAM 与离线存储，无需第三方服务 |
| 无账号体系，密钥仅存本机 | 换机即丢是其最大差评；本项目坚持 JID + OMEMO 密钥备份 |
| 论坛 / 博客的全量复制语义 | 群聊走 XEP-0045 / XEP-0369，不做全复制 |
| 自定义 Doze 对抗 | 用标准推送唤醒；不在本阶段与厂商 ROM 对抗 |

## 3. 协议层面的两条硬教训

1. **不要自创密码学协议**。Briar 的 BHP v0 因缺少 `DH(eskA, epkB)`，双长期密钥泄露即失去前向保密（CVE-2023-33982，1.5.3 修复）。本项目的 B 轨虽为自定义扩展，但**只组合既有的成熟原语**（X3DH 四 DH + ML-KEM-768 + HKDF-SHA512），不发明新的密钥协商结构；A 轨则完全交给 `omemo_dart`，以保证与 Conversations 互通。
2. **自研协议的互通测试必须双端**。Briar 生态内自洽但对外零互通。本项目的对应防线是：M2 阶段就用真实 Conversations 验收 A 轨，而不是只用本客户端两个实例互测。

## 4. 合规注意

- Briar Android 为 **GPLv3-only**，桌面端为 AGPLv3。若将来直接复用其代码片段，**必须保留 `only`，不可改为 `or-later`**；本项目为 GPL-3.0-or-later，方向兼容但条款更严格，需逐文件标注。
- 其依赖（BouncyCastle MIT、Tor BSD-3、onion-wrapper GPLv3）均与 GPLv3 兼容；若引入 `dont-kill-me-lib`（GPLv3）需注意传染性。

## 5. 后台与推送决策（M7）

采纳：`FCM + XEP-0357 Push + XEP-0198 Stream Management + XEP-0313 MAM`。
不采纳：常驻前台服务作为唯一手段（仅作「实时模式」的可选增强）。
F-Droid 风味无 FCM 时，用 `WorkManager` 周期唤醒替代长连接，并接受延迟。
发布门禁需包含电池/后台实测矩阵（Briar 的教训：Honor、Nokia、三星等机型在 Doze 后仍会丢连接）。
